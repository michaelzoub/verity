# System boundaries

`apps/web` uses the generated client from `artifacts/openapi/openapi.json`. Marketplace and result pages render API projections only. Public challenge projections include a complete submission specification, public examples, and starter bundle, but never private grader source or hidden outcomes. Company mutations require a real Privy access token; challenge creation is idempotent, and funding is accepted only from the Privy-connected EVM wallet bound into the draft on Monad Testnet.

The API stores immutable private grader bytes only in private Supabase Storage and metadata, nonces, jobs, settlement claims, projections, event identities, and checkpoints in Supabase Postgres. There is no JSON persistence, filesystem object store, Anvil path, auth flag, or fixture-backed frontend path.

The worker claim endpoint returns job-bound private-object references, never grader or submission bytes. Only the separately deployed trusted worker has Supabase service credentials. Every preflight and grading attempt creates a fresh E2B sandbox with internet access disabled, executes the fixed language entrypoint, validates the strict `GraderResult`, and destroys the sandbox.

Direct human/agent submissions share one backend endpoint and contain a path-validated real source-file bundle, final output, and artifacts. Required function-call validation is limited to platform-executed agent runs submitted through the platform HMAC boundary. The API rejects client-supplied traces; the worker accepts a trace only when the stored envelope is marked with the authenticated platform execution identity, then validates sequence, counts, order, argument schemas, and output schemas before the private grader runs.

Privy verifies company identity only. It never determines challenge ownership from request bodies, signs settlements, chooses payout recipients, or controls escrow. A payout wallet is recovered from the one-time challenge-bound verification message; the recovered address is the only address persisted and signed into settlement.

`ChallengeFactory` creates one escrow per challenge ID. The company wallet funds creation and becomes the immutable refund recipient. The separate backend settlement account signs EIP-712 and broadcasts `finalize`. A passing score pays the verified wallet once; below-threshold scores finalize without payout; invalid, timed-out, unevaluable, or grader-error results never cross the settlement boundary. After the deadline, an unpaid escrow can only refund its remaining balance to the company wallet.

The indexer consumes confirmed escrow creation, submission-recorded, finalization, payout, and refund events, stores event IDs and projections atomically, checkpoints confirmed block hashes, and exposes funding, grading, settlement, payout, expiration, and refund state through the API. Public submission responses never expose private grader feedback/metadata, sandbox IDs, private failure details, signatures, logs, secrets, or storage paths. Contract and database guards cover duplicate payloads per wallet, duplicate jobs, stale worker attempts, nonce replay, duplicate events, double payouts, early refunds, and settlement/refund races.
